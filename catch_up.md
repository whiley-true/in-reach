# Scripting: where we are

Written 2026-09-21 as a design starting point: what the scripting side of in-reach **does today**, with real examples
(every output below was produced by running the tools on a scratch project, not written by hand), where it stops, and
the questions the redesign has to answer. Nothing here proposes code; section 10 lists the decisions.

Versions this describes: `in-reach` 0.3.0 plus unreleased work (the `within-reach` dependency), `in-reach-ide` 0.1.0,
`within-reach` 0.1.0 (0.2.0 pending). Source of truth for details: `CLAUDE.md` (what the code does), `next_steps.md` (what is
left), `TO_IMPLEMENT_(LATEST).md` (the original design, partly superseded -- its §4.8 and §13 are the closest to what exists).

---

## 1. The three levels at a glance

| | **1. One file** | **2. One file + profiles** | **3. A script project** |
|---|---|---|---|
| You edit | `script/output.txt` | `script/output.txt` and `script/env/*.env` | `script/project.toml`, `blocks/*.mgl`, `modules/*/` |
| What is built | that text | that text with `${CONSTANTS}` and `-- @if` blocks resolved for the active profile | the linker's assembled script (`build/Compiled.txt`) |
| Storage slots | you write `global.number[3]` | same | you write a *name* (`-- @number g_score`); the linker picks the slot |
| Engine resources (trait sets, widgets, options) | edit `settings/script_settings.json` by hand or in RVT | same | declared in code (`-- @trait ...`), created for you |
| Checks before you build | none (errors come back from the compiler on Apply) | same, plus a profile/constant error is located | project model + linter + allocator + fusion, on every save |
| Reuse / sharing | copy-paste | copy-paste | modules: vendored from a folder or git, pinned in `project.lock` |
| Documentation and tags | plain comments only | plain comments only | annotations are *parsed*; nothing consumes them yet (section 5.2) |
| Turned on by | the default for a new project | adding `script/env/<name>.env` (a new project already has `dev` and `release`) | `in-reach create-project` (or the IDE's "Create Script Project") |

Two facts that matter for the redesign:

- **Level 2 is not a separate mode.** It is level 1 plus the profile preprocessor, which runs on every build of a
  single-file project whether or not any profile exists (no profile and no directives means the text is unchanged).
- **Level 3 is entered one way.** `create-project` copies `output.txt` verbatim into `blocks/main.mgl`, adds `project.toml`,
  and from then on `output.txt` is not compiled. There is no way back short of deleting `project.toml`.

## 2. How a build works

```
                      settings/*.json  (game options, script settings, strings)
                              |
 script ---------------------+------------------> compile ------> build/dist/<name>.bin
   level 1/2: script/output.txt --preprocess--/                       |
   level 3:   script/ (project) --link--> build/Compiled.txt          +--> build/*.autogenerated.json
                                                                           (a re-extraction of what was built)
```

- **The compiler** (`megalo_compiler.py`) is in-house: it builds native trigger objects directly. Anything outside the subset
  it covers falls back to the native compiler (`compile_script()`), which reports errors with line numbers. It compiles 423
  of 423 shipped real-world scripts. Native code is the *backend* (the `.bin` writer, the decompiler, the engine's limits);
  the front end is Python.
- **Every build starts from the project's frozen base `.bin`** (`.in-reach/init_gametype/<id>.bin`, the file the project was
  created from), never from the previous build. That is why generated names must be deterministic.
- **Apply** builds *and* reconciles `settings/`: forge labels and script strings the script created are written back, and a
  trait set or option grows the variant to match `settings/script_settings.json`.
- **A build runs in a child process** (a native crash can't take the IDE down); the CLI and IDE both go through it.

### Files in a project folder (`<root>/<id>/`, next to `<root>/.in-reach/`)

```
script/
  output.txt                 level 1/2: the whole script.  Level 3: no longer compiled.
  env/dev.env, release.env   profiles (FLAGS=..., NAME=value);  env/active_profile.txt names the active one
  project.toml               level 3 only
  blocks/*.mgl               level 3: a block per file; the name is the file stem, upper-cased (setup.mgl -> SETUP)
  modules/<name>/            level 3: module.toml + *.mgl
  project.lock               level 3: pins for modules that have a source
settings/
  settings.json              game options (mirrors the .bin)
  script_settings.json       forge labels, options, trait sets, widgets, stats
  strings.json               every string table, per language
build/                       everything generated; never hand-edit
  Compiled.txt               the script as it is compiled (see "views")
  Decompiled.txt             the built .bin's script as RVT shows it
  link_map.json, declarations.mgl     level 3 only
  dist/<name>.bin            the built game variant
```

### The three views of the script

| View | What it is | Where | Command |
|---|---|---|---|
| **megalo** | the source as written | `script/output.txt`, or every `.mgl` file of a project | `in-reach show --view megalo` |
| **rvt+** | the script as compiled: profile applied; for a project, the linker's assembled text | `build/Compiled.txt` | `in-reach show --view rvt+` |
| **rvt** | what RVT shows for the built `.bin`: no modules, no profile, no annotations, the compiler's own layout (`inline:` blocks) | `build/Decompiled.txt` | `in-reach show --view rvt` (needs a build) |

## 3. Level 1 -- editing one file

The script is `script/output.txt`, ordinary Megalo. A new project's file is the *decompile* of the game variant it started
from, so you begin with a working script.

```
for each player do
   if current_player.score >= 5 then
      game.end_round()
   end
end
```

What you get today:

- **In the IDE:** a text editor with Megalo syntax colouring (keywords, `current_player`/`global`/..., strings, numbers,
  comments), a Find/Replace bar, the Dashboard's "View Compiled" and "View Decompiled" buttons, **Apply** (Ctrl+Shift+B).
  Errors come back in Apply's failure dialog and on the Problems tab, at `script/output.txt` line and column.
- **On the command line:** `in-reach build <folder>`, `show`, `export --out`, `launch rvt`.
- **RVT round trip:** the bundled ReachVariantTool has script editing switched off, so RVT only edits *settings*, which flow
  back into `settings/*.json`. If some other tool changes the built `.bin`'s script, the IDE offers to pull it into
  `output.txt` (asking first if that would lose unapplied edits, comments or `${}` directives).
- **Skip-if-unchanged:** if `output.txt` equals what the base `.bin` already decompiles to, the compile is skipped (the
  native compile/decompile round trip is not a fixed point, so recompiling an untouched script would change it).

You write engine indexes yourself (`global.number[3]`, `script_traits[0]`); nothing checks that two parts of the script
don't fight over a slot.

**Gaps at this level**

- Nothing is checked until you Apply. There is no parse-as-you-type, no Problems entries before a build, no autocomplete
  or hover.
- **Apply is not enabled by script edits alone** in a single-file project (it enables when a `settings/` file differs from its
  last build). Launching RVT and Export compile anyway. This is a known inconsistency with level 3, where script edits do
  enable it.
- The Documentation panel is a placeholder.

## 4. Level 2 -- one file with profiles

A **profile** is `script/env/<name>.env`; the active one is named in `script/env/active_profile.txt`. New projects start with
`dev` (active) and `release`.

```
# script/env/dev.env
FLAGS=DEV
SCORE_TO_WIN=5

# script/env/release.env
FLAGS=RELEASE
SCORE_TO_WIN=50
```

Before compiling (and before `Compiled.txt` is written) the preprocessor applies it:

- `${NAME}` becomes the constant's value. A value is a signed 16-bit number, a percentage, a name, or a quoted string --
  nothing that could smuggle in code. A constant nobody defined is an error located at its line. Comments are left alone.
- `-- @if FLAG` ... `-- @end` keeps the block only when the flag is on (`-- @if !FLAG` inverts; `-- @else` flips; they nest).
  Each directive is alone on its line and is an ordinary comment to Megalo, so the file still compiles with everything kept.
- **Line numbers never shift:** a removed line becomes empty and a substitution never adds a newline, so an error at line 40
  points at line 40 of the file you edit.

Example (`script/output.txt`, real output for both profiles):

```
-- Give every player a point when they reach the score threshold.
-- @doc ends the round when someone reaches the target
for each player do
   if current_player.score >= ${SCORE_TO_WIN} then
      game.end_round()
   end
-- @if DEV
   current_player.score += 1   -- dev: score faster
-- @end
end
```

`in-reach show --view rvt+` with `dev` active (`SCORE_TO_WIN` is 5, the DEV block stays):

```
for each player do
   if current_player.score >= 5 then
      game.end_round()
   end
-- @if DEV
   current_player.score += 1   -- dev: score faster
-- @end
end
```

...and with `release` active (50; the DEV block's lines are blanked, the directives remain as comments):

```
for each player do
   if current_player.score >= 50 then
      game.end_round()
   end
-- @if DEV

-- @end
end
```

`in-reach build --profile dev` builds one profile without changing the active one; `in-reach profile list|set` and the IDE's
status-bar "Profile: dev" segment / "Select Build Profile" switch it. The decompiled result of the dev build is:

```
for each player do
   inline: if current_player.score >= 5 then
      game.end_round()
   end
   current_player.score += 1
end
```

**Documentation and tagging at this level** -- what exists is: comments, and `Notes.txt` (a per-project notepad in the
Dashboard). `-- @doc` in the example above is *only a comment* here: annotations are read only in a script project. Nothing
extracts documentation, and there is no notion of a tag on a single-file script.

**Stamp Release** (version history) asks for confirmation if the project has a `release` profile and is not on it.

## 5. Level 3 -- a script project (the advanced tier)

Everything in this section applies once `script/project.toml` exists. `in-reach create-project` on the level-2 example:

```
script/project.toml            script/blocks/main.mgl
-------------------            ----------------------
[project]                      (the old output.txt, verbatim, including its directives and ${...})
name = "Demo Game"
[blocks]
order = ["MAIN"]
```

`in-reach link` then assembles (release profile active; the `@doc` line is dropped, the `@if DEV` block is resolved):

```
-- in-reach build: Demo Game  profile=release  flags=RELEASE
-- Auto-generated and non-editable. Edit script/ and rebuild.

-- MAIN (blocks/main.mgl)
-- Give every player a point when they reach the score threshold.
for each player do
   if current_player.score >= 50 then
      game.end_round()
   end

end
```

### 5.1 Blocks, modules, fragments

- A **block** is a file in `blocks/` (hand-written code, in order) *or* exists because a module writes `-- @fragment BLOCK.name`.
  `project.toml`'s `[blocks] order` lists them; unlisted blocks build after the listed ones in first-seen order.
- A **module** is a folder with `module.toml` and `.mgl` files. It declares its own storage and resources and contributes
  **fragments**: loop bodies added to blocks. `[[modules]]` entries in `project.toml` list which modules build (`enabled =
  false` keeps one without building it), with per-module `params`.
- Blocks are code; fragments are code *plus* a header. Two neighbouring fragments in a block with the same loop, gate and
  preamble are **fused** into one trigger when a conservative read/write analysis finds nothing one writes that the other
  reads on a different iteration.

The shipped sample (`samples/script_project/`) has two modules that both add to a `TICK` block:

```
# modules/scoring/scoring.mgl                       # modules/speed_boost/speed_boost.mgl
-- @ptimer p_second default=1                        -- @trait t_fast { name = "Fast", desc = "50% faster",
-- @fragment TICK.score                                                  movement_speed = "value_150" }
-- @loop player                                      -- @fragment TICK.boost
current_player.p_second.set_rate(-100%)              -- @loop player
if current_player.p_second.is_zero() then            current_player.apply_traits(t_fast)
   current_player.score += 1
   current_player.p_second = 1
end
```

`in-reach link` (real output):

```
blocks   SETUP -> TICK -> WIN_CHECK
fused    TICK <- scoring.score + speed_boost.boost
budget   global.number 1/12  player.timer 1/4  traits 1/16
```

`build/Compiled.txt`:

```
declare global.number[0] with network priority low
declare player.timer[0] = 1

alias g_started = global.number[0]
alias p_second = player.timer[0]
alias t_fast = script_traits[0]

-- SETUP (blocks/setup.mgl)
on init: do
   g_started = 1
end

-- TICK (fused: scoring.score, speed_boost.boost)
for each player do
   -- scoring.score
   current_player.p_second.set_rate(-100%)
   if current_player.p_second.is_zero() then
      current_player.score += 1
      current_player.p_second = 1
   end
   -- speed_boost.boost
   current_player.apply_traits(t_fast)
end

-- WIN_CHECK (blocks/win_check.mgl)
for each player do
   if current_player.score >= 10 then
      game.end_round()
   end
end
```

### 5.2 Annotations (`-- @name ...`)

Comments that start their line with `@`. They are ordinary comments to Megalo, parsed by a second small parser
(`megalo_ast/annotations.py`) that never raises: a malformed one is reported at its line and column and the good ones around it
still work. A second `--` starts a free-text note. `-- @if/@else/@end` are profile directives, not annotations.

| Group | Annotations | Meaning today |
|---|---|---|
| Storage | `@number @object @player @team @timer NAME` (global), `@pnumber ... @ptimer` (per player), `@onumber ... @otimer KIND.NAME` (per object of a kind), `@tnumber ... @tteam TEAM.NAME` (per team); options `priority=`, `default=`, `owns_default=` | the linker allocates a slot, emits `declare` (priority/default) and `alias NAME = <slot>` |
| Bitfield | `@bitfield KIND.NAME { a, b, c }` | one object number, an `alias flag_a = 1`, `flag_b = 2`, ... each (bit 15 reserved) |
| Engine resources | `@trait NAME { field = value }`, `@option NAME { type = "toggle"\|"range", ... }`, `@widget NAME { position = n }`, `@label NAME = "text"` | trait sets / options / widgets are created and written to `settings/script_settings.json`; `name`/`desc` become in-game text; a label is substituted where the script says `with label NAME` |
| Structure | `@block NAME`, `@fragment BLOCK.name`, `@loop player\|object\|team`, `@gate <cond>`, `@guard <cond>`, `@preamble NAME` + `@provides n:type` + `@guard-end`, `@fusion auto\|never\|force:G` | assemble triggers; see fusion below |
| Documentation | `@doc text`, `@see TAG`, `@assumes BLOCK` | `@doc`/`@see` are **parsed and kept on the model, used by nothing** (no output, no panel). `@assumes BLOCK` is checked (IR016: the block must build earlier) |
| Tagging | `@traits layer=NAME`; `module.toml` `tags`, `features`, `summary`, `description`, `license`, `authors`, `min_in_reach` | **parsed and validated, used by nothing** -- the trait-ordering lint (IR009) that `layer` was for is not built |

Rules worth knowing: an annotation must start its line (`x = 1 -- @doc` is a plain comment); annotation *arguments* are the
only place `${}` substitution reaches inside a `--` comment (so `-- @ptimer t default=${interval}` works); `@fusion
subroutine` is accepted and **refused with a warning** (treated as `never`).

### 5.3 What the linker decides

- **Allocation is stable.** Names are placed in declaration order, each taking the lowest free slot; a slot your hand-written
  code already uses (`global.number[0]`) is never allocated; `[pins]` in `project.toml` fix a name to a slot. Object storage
  is per *kind* (no object is two kinds, so two kinds can share `object.number[0]`); an object slot has one declared default.
- **Engine limits** (checked): global number 12 / timer 8 / team 8 / player 8 / object 16; per-player number 8 / timer 4 /
  team 4 / player 4 / object 4; per-object number 8 / timer 4 / team 2 / player 4 / object 4; per-team number 8 / timer 4 /
  team 4 / player 4 / object 6; per-trigger temporaries number 10 / team 6 / player 3 / object 8; option 16, trait set 16,
  widget 4, stat 4 (a *variant* holds at most 320 triggers, 512 conditions, 1024 actions).
- **Resources keep their index** across links and are never dropped. If you edit a resource's entry in RVT or
  `script_settings.json`, your edit wins (the linker records what it last wrote and compares).
- **Nothing is written unless everything succeeded** (`Compiled.txt`, `declarations.mgl`, `link_map.json`, and only then
  `settings/script_settings.json`), and only files whose content changed.
- **Line mapping:** a compiler error in `Compiled.txt` is reported at the source file and line (`link_map.json` records
  which output lines came verbatim from which source lines).

`link_map.json` (excerpt, real):

```json
{ "order": ["SETUP", "TICK", "WIN_CHECK"],
  "storage": { "g_started": {"slot": "global.number[0]", "owner": "blocks/setup.mgl"},
               "p_second":  {"slot": "player.timer[0]",  "owner": "module scoring"} },
  "resources": { "t_fast": {"kind": "trait", "index": 0, "owner": "module speed_boost",
                            "text": {"name": "Fast", "desc": "50% faster"}} },
  "budget": { "global.number": {"cap": 12, "used": 1}, "traits": {"cap": 16, "used": 1},
              "counters": {"triggers": {"cap": 320, "used": ...}} },
  "fusion": { "groups": [{"trigger": "TICK", "fragments": ["scoring.score", "speed_boost.boost"],
                          "saved": {"triggers": 1}}], "declined": [] } }
```

(`counters` appear after a real build, measured on the built variant.)

### 5.4 Checks

`in-reach check` (and the IDE, on every save) reports located, coded diagnostics:

```
blocks/setup.mgl:2:1: error: g_started is already declared at blocks/setup.mgl:1 [IR006]
   (every name is one thing across the whole project; rename one)
1 error, 0 warnings
```

| Built | Rule |
|---|---|
| yes | IR004 temporaries over the cap (after fusion) - IR005 timer with a network priority - IR006 name/slot declared twice - IR007 `true`/`false` used as a value (`x = true`; a bare call argument like `set_hidden(true)` is fine) - IR010 (a *warning*) unlabelled `for each object` per tick - IR011 bitfield over 15 flags - IR012 a variant counter within 10% of its cap - IR013 block-order cycle - IR015 unresolved constant / parameter - IR016 `@assumes` order - IR018 a forced fusion the analysis would have declined |
| no (need an engine catalog that doesn't exist) | IR001 dereference depth - IR002 parenthesised `or` - IR003 action used as a value - IR008 - IR009 trait application order - IR014 - IR006b |

### 5.5 Sharing modules

A module is a folder; sharing is copying it, made traceable. `in-reach module add <folder | git+URL[@rev][#subdir=path]>`
**vendors** the files into `script/modules/<name>/`, records `source = ...` on its `[[modules]]` entry, and pins it in
`script/project.lock` (version, source -- a git source pinned to the exact commit -- and a content hash that ignores CRLF vs
LF). `module verify` errors on a changed or missing module (the loader only warns, since editing a vendored module is
legitimate); `module update` re-fetches; `module lock` re-pins your edits. No registry: path and git URL only, by decision.

### 5.6 Editing the composition (what a UI would drive)

Text-level edits that keep comments and line endings: `in-reach module enable|disable`, `block-order A B C`,
`move-fragment module.name BLOCK` (rewrites the `-- @fragment` line). All also `in_reach.api` functions.

### 5.7 Precedence rules (easy to get wrong)

- **Constants:** `project.toml [constants]` are defaults; the active profile overrides them; a module's `params` beat both, in
  that module's files only. A constant defined as `"${OTHER}"` follows OTHER's final value.
- **Profile:** the IDE's choice (`script/env/active_profile.txt`) wins over `project.toml [project] profile`.
- **Settings vs code:** a resource entry you changed in `settings/` wins over the module's declaration; the *text* of a
  declared trait set / option (its name and description) is owned by the code and rewritten every build.

## 7. Known gaps, by level

**Level 1/2**
- No checking before Apply; no autocomplete/hover; no per-line diagnostics as you type.
- Script edits alone don't enable Apply (only `settings/` changes do).
- Annotations and lint do not run: a level-1/2 script gets none of level 3's checks (name clashes, limits, temporaries).
- Documentation and tags: none beyond comments and `Notes.txt`.

**Level 3**
- `@doc`, `@see`, `@traits layer`, module `tags`/`features` are parsed and unused; no generated overview, README linking or
  Documentation panel.
- The lint rules that need an engine catalog aren't built (table above); no catalog, so no autocomplete either.
- `@fusion subroutine` is refused (whether a called trigger sees the caller's temporaries is unverified without an in-game
  probe); fusion savings are reported as triggers and preambles only.
- A widget or stat has no in-game text to name; stats can't be declared in code.
- The RVT script pull-back does nothing in a project, and the way in from level 1/2 is one-way.
- Nothing has been played in the game: the fused/allocated script is verified by the compiler and the analysis, not the engine.

**Across levels**
- Errors are reported at source lines only for a project (linker line map); a single-file project's errors are in
  `output.txt` coordinates (which is right, but the preprocessor's constants can't be traced from the compiler's view).
- The simulator, probe gametype and the Python front end are dropped/deferred.

## 9. Glossary

**Block** a build stage, one file or fragment-only. **Fragment** a loop body a module adds to a block. **Fusion** merging
neighbouring fragments into one trigger. **Preamble** a shared prologue several fragments use. **Profile** a set of
constants and flags (`script/env/<name>.env`). **Flag** a name a profile turns on (`FLAGS=DEV`). **Constant** a `${NAME}`
value. **Kind** a class of object that shares per-object storage. **Vendored** copied into the project. **Link** to assemble
a project into `Compiled.txt`. **Apply** to build the `.bin` and reconcile `settings/`.

## 10. Decisions the redesign needs

1. **Are the levels modes or one spectrum?** A level-3 project with a single block *is* level 2 plus checks. Options:
   keep three explicit modes; or make every project a project (a new one starts with one `main` block and the checks on),
   with "single file" just being what one block looks like in the editor. The second removes the one-way door and the
   "no checks at level 1/2" gap, at the cost of a bigger default.
2. **What does "documentation" mean, concretely?** Candidates: `@doc` text rendered next to code in the editor; a generated
   overview (blocks, modules, budget, fusion) as a document; a per-module README linked by `@see`; a Documentation view in the
   IDE; something an LLM can read. Which of these, and does it work at level 2?
3. **What is a tag?** Today: `@traits layer=`, and `module.toml` `tags`/`features`. Are tags for *finding* things (library
   search, filtering the Scripts view), for *checking* things (the layer order lint), for *grouping* (a feature list a module
   closes), or all three? Do single-file scripts get tags (e.g. a leading `-- @tags` line)?
4. **Do annotations and the linter apply to a single file?** If `-- @doc` and `-- @number` should work at level 2, the parser
   and checks must run on `output.txt`; the linker's allocation is what makes storage names meaningful, so the question is
   how much of it a single file gets.
5. **Editor behaviour to design before building:** when checks run (on save vs as you type), what Apply means for script
   edits at each level, what the Problems tab shows for a single file, and how the three views are presented (tabs of one
   script, or separate documents).
6. **Profiles as tags?** A profile flag (`DEV`) and a documentation/feature tag are close relatives -- one says "include this
   for a build", the other "this belongs to that". Worth deciding whether they are one concept.
7. **The shared-module story in the UI:** module add/update/verify exist only on the command line; the composition board
